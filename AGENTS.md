# Notes for agents

Home Assistant integration for the Sony LSPX-P1 projector over Bluetooth LE, plus a dashboard card. Setup and commands are in the README's Development section; skills in `.agents/skills` cover translations, screenshots, releases and protocol research.

## Pitfalls

- **One connection at a time.** The projector serves one Bluetooth client; the integration disconnects soon after each poll so the phone app and proxies stay usable. Keep it that way.
- **Most commands are only known from the decompiled app.** Mark anything not tried on a real projector as such in release notes, and make a failing read affect only its own entities (per-field errors in `read_state`, never a failed poll).
- **Commands run between a poll's reads.** A poll does not hold `_switching`; what a command applies through `async_command` while one is in flight is replayed onto its result (`_applied`), so a stale read cannot undo it. A new path that changes the state optimistically must go through `async_command` (or log its apply) to keep that.
- **Replies can come twice** (seen through Home Assistant), and a connection can start with the last frame of the one before; replies tell which command they answer only by opcode, so `_exchange` waits for the copy before sending the last reply's opcode again (`DUPLICATE_WINDOW`). The fake projector repeats frames with `duplicate_delay` and `replay_on_subscribe` (`tests/test_duplicate_replies.py`).
- **Home Assistant picks the Bluetooth path.** With several adapters or proxies, habluetooth's client chooses one for each connection attempt from the address alone (by signal, adjusted for failures and, in recent releases, busy or full adapters); the `BLEDevice` passed in does not choose it, and no public API pins or prefers one (only overriding private habluetooth methods would, which differ between the minimum and current releases). The README's Limitations tell users how to keep connections off a proxy.
- **Replies can be slow.** Source switches answer only when done (up to 60 s, `SWITCH_REPLY_TIMEOUT`); other commands 8 s. A timeout drops the connection.
- **Setup must not depend on the projector.** It is often off; entities go unavailable, they must not disappear. Every entity goes unavailable while polls fail, so a feature meant to recover the projector needs to stay available (see the Restart button's `always_available`).
- **Entry update listeners also fire for discovery.** Home Assistant updates the config entry when another Bluetooth adapter or proxy discovers the projector (`discovery_keys`), so the options listener in `async_setup_entry` reloads only when the options changed; `OptionsFlowWithReload` is newer than the minimum Home Assistant version in `hacs.json`.
- **Every user-facing string exists in 16 languages**: `translations/` (generated, see the translations skill) and the card's `WORDS` table.
- **The card** (`frontend/sony-lspx-p1-card.js`) is plain JS with no build step. It registers itself only after Home Assistant's scoped custom-element registry exists (`registerCard`). Every control change goes through `_act()`: optimistic value at once, sent through `LANES` (one call per lane, latest value wins, power first) so related settings never race; try changes with `tools/screenshots/demo_ha.py --slow`. Its layout depends only on the card's width, never on the state or its wording: the state word always shows (on its own line), and a state change never moves, shows or hides anything else in the header or the dialog's bar (`test_header_layout_ignores_the_state`); the battery chip stays while the battery is unavailable and goes only for a battery entity without a state (disabled). Changing it means retaking the README screenshots.
- **Card tests** (`tests/test_card_ui.py`, part of `pytest`) drive the real card in headless Chrome on `tests/card/harness.html` (fake `hass`; fake `setTimeout`, so time passes only with `T.tick(ms)` and page code must not wait on timers). They skip locally without Chrome (set `CHROME=`) but fail in CI. Tests that need no Home Assistant override the autouse `auto_enable_custom_integrations` fixture.
- **Checks** are ruff, `.venv/bin/mypy` (strict, integration only; `platform = "linux"` so BlueZ code is checked on macOS too) and `pytest --cov` (above 95% in every module, as the quality scale asks; keep `quality_scale.yaml` honest). Tests run serially by default; `-n auto` means two workers (`tests/conftest.py`), because each also starts a headless Chrome: do not ask for one per core, and when other agents are working on this machine run only the test files you changed and leave the full suite to CI. The coordinator uses `always_update=False`: a test poll that returns the same data notifies no listeners, so change something first.
- **Minimum Home Assistant** (`hacs.json`, stated in the README too): CI's `test-minimum` job runs the tests on that release with its `package_constraints.txt`, reading the version from `hacs.json` (raise its Python when needed). Until 2025.8 it ships bleak 0.22, whose `BLEDevice` also requires `rssi`: build one with `client.make_ble_device`.
- **Typing:** recent Home Assistant types form and service schemas as `probatio.Schema`; pass voluptuous schemas with a commented `type: ignore[arg-type]` (see `config_flow.py`) so older versions keep working.
- **Tests and time:** freezegun's `freezer` freezes the event loop's clock too, so the fake projector's replies hang; patch the module's `dt_util` instead (see `tests/test_clock.py`). `async_fire_time_changed` also fires the client's own timers (idle disconnect), so advancing time drops the fake link.
- **Diagnostics stay redacted and free.** Smartphone names are redacted from the state; the `bluetooth` section passes through `_scrub` (error texts from bleak carry Bluetooth addresses, of proxies too). The link counters (`LinkStats`) and recent polls are recorded as things happen: downloading diagnostics must not add Bluetooth traffic (the Weather read is the one exception, bounded by a timeout).
- **Bluetooth first; Wi-Fi is opt-in.** Bluetooth is how the integration works by default. Most projectors are never on Wi-Fi (hard to set up from the app), so an entity that needs the projector on Wi-Fi is disabled by default (the settings over Wi-Fi). The clock goes through the Bluetooth tunnel to the projector's HTTP API (`tunnel.py`, `LSPXClient.web_request`), over Wi-Fi only when that fails; a tunnel request holds the link (the client's lock and `_switching`) for all its steps, and nothing else uses the tunnel yet.
- **Entities disabled by default** (those over Wi-Fi, Usage time, Bluetooth signal): there is no fixture to enable them in tests; patch `LSPXWebEntity._attr_entity_registry_enabled_default` (see `tests/test_web_settings.py`) or `LSPXSignalSensor`'s (see `tests/test_signal_sensor.py`), or set the same attribute on `LSPXSensor` (it does not exist there: `patch.object(..., create=True)`, or `monkeypatch.setattr(..., raising=False)` when a test must undo it to see the real default) for a description's `entity_registry_enabled_default=False` (see `usage_enabled` in `tests/test_init.py`).
- **Git:** `main` takes only squash-merged pull requests (a repository ruleset refuses a direct push, the version bump of a release included): work on a branch, open a draft pull request and merge it once its checks pass. The squash commit takes the pull request's title as its own, followed by the branch's commit messages, so write the title as a commit message in `main`'s style. The pull request's four checks must pass before it can merge, and release tags (`v*`) cannot be moved or deleted. End commit messages with the `Co-Authored-By` trailer; release with the release skill.
- **Never commit** anything from the official app (APK, decompiled code); it lives in `.notes/`, which is excluded in the main checkout's `.git/info/exclude` (not `.gitignore`).
